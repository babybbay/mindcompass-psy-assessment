## 1. 如何分解问题

### 初始阶段（Codex）——按产品流程拆解

把"可交互测评平台"拆成七个纵向模块，逐个交付、逐个验证：

1. 知情同意与隐私说明（目的/数据用途/研究边界/非诊断声明）
2. 六个问卷入口（BFI-2 60题、爱情态度42题、TriPM 58题、AI态度/冒险/团队各12题）+ 旧版28题保留
3. 服务器端评分引擎（反向题、维度聚合、总分规则）
4. 结果页（维度图表、子维度、来源与谨慎解释）
5. D1 数据层（参与者、同意、版本快照、答卷、反馈五张表）
6. 研究者后台（人数、分布、平均分、完成率、导出）
7. 部署与真实试用

### 迁移阶段（Claude Code）——按风险拆成四任务

chatgpt.site 在国内无法访问后，我向 Claude Code 提出四步计划并要求逐项完成：

1. **本地跑起来并调试**——确认导出代码本身没问题
2. **接上数据库**——答卷真实落库
3. **验证计分正确性**——补测试，确认评分键无转录错误
4. **配置部署**——国内外都能访问

每个任务再向下拆：任务 4 拆成"平台选择 → 认证改造（自托管后原身份头可被伪造）→ 部署管线 → 域名与账号准备 → 发布 → 线上实测"。任务 3 拆成"先审计（读代码+对文献）→ 再补硬编码测试 → 最后端到端复验"。

## 3. 智能体如何帮助设计架构

### Codex 设计的数据与计分架构

- **不可变量表快照**：量表配置以 version + 哈希存入 `mc_scale_versions`，答卷引用快照评分——以后改量表不会改写历史答卷的解释
- **原子完成**：答案与得分同一条记录一次条件更新写入，避免"有答案无分数"的中间态；修订号（revision）实现乐观并发
- **去标识化会话**：随机 participantId + 令牌 SHA-256 存库，HttpOnly Cookie 关联；管理员身份与参与者表隔离
- **保留策略**：草稿 7 天过期、完成 180 天保留、撤回级联删除，每日 cron 清理并留运行记录

### Claude Code 设计的迁移与认证架构

- **平台依赖地图**：探索代理产出逐行引用清单，识别出唯一硬依赖是"管理认证信任 Sites 网关注入的 `oai-authenticated-user-id` 头"——自托管环境任何人都能伪造该头
- **认证重构**：`ADMIN_PASSWORD` 密码登录 → 服务端校验后签发 HttpOnly SameSite=Strict Cookie（`mc_admin`）→ 所有管理 API 复检 Cookie；未配置密码一律 401；恒定时间比较 + 失败限速 + 固定失败延迟
- **部署管线**：`scripts/deploy.mjs` 一条命令完成"构建 → 替换真实 D1 绑定/变量/路由 → 远端迁移 → wrangler deploy"；敏感配置存于 gitignore 的 `deploy-config.json`
- **网络层诊断结论**：实测证明国内 DNS 解析正常、TCP/TLS 直连成功，封锁来自 OpenAI 在 Cloudflare 的地域 WAF 规则——因此迁移到自有 Cloudflare zone 即可解决，无需备案

分层验证，每一层都实际跑过：

| 层级 | 内容 | 结果 |

| 浏览器端到端 | Playwright（系统 Edge）：桌面 1440×1000 + 手机 390×844，覆盖六问卷全流程、同意保护、恢复、后台登录 | 12/12 通过 |
| 静态检查 | tsc 类型检查、ESLint、构建、敏感模式扫描 | 全部通过 |
| 手动计分复验 | `manual-score-verify.mjs` 对线上同构流程提交三组答案：全3分→各维度3；正向5反向1→应全5；正向1反向5→应全1 | 9/9 断言通过 |
| 线上端到端 | `live-verify.mjs` 对生产环境跑完整流程：首页→同意→答题→计分→结果页→管理登录→汇总→撤回删除 | 12/12 通过 |
| 安全复测 | curl 伪造 `oai-authenticated-user-id` 头访问管理 API → 401；错误密码 → 401；登出后 Cookie 失效 | 全部符合预期 |

## 6. AI 智能体犯过的错误（按阶段记录）

### Codex 阶段（均有测试或复测证据）

1. 旧版均分提前舍入 → 混合作答手算 3.25 的回归测试暴露
2. 前端可伪造有效范围的分数 → 改为服务器重算
3. 公开的固定管理码 → 改为身份白名单（后又改为密码登录）
4. 草稿不持久化、导航可绕过同意框 → 用户复测发现后修复并补 e2e 回归

### Claude Code 阶段（本次迁移中真实发生）

5. **原代码信任网关注入的身份请求头**——部署在 Sites 平台时安全，但这是平台专属假设；自托管后任何人 `curl -H "oai-authenticated-user-id: xxx"` 即可成为管理员。由探索代理在迁移前审计发现，是本次必须重构的原因
6. **计分测试存在同义反复**——边界测试用配置自身的反向标记构造答案，反向题转录错误无法被发现。审计报告指出后补硬编码清单
7. **线上验证脚本漏带 Origin 头**——DELETE 撤回请求被 403 拒绝。这是站点的来源校验在正常工作，暴露的是脚本缺陷；修复后重跑全部通过
8. **部署脚本 `delete config.workers_dev` 处理不当**——wrangler 仍在部署流程中调用 workers.dev 子域名同步端点；后改为显式 `workers_dev: false` 并查明 wrangler 源码中的无条件调用逻辑
9. **诊断初判偏差**——最初推测"国内打不开=GFW 拦截域名"；实测（国内 DNS 解析、直连 TCP/TLS、浏览器复测）证明是 OpenAI 的 Cloudflare 地域规则。教训：先实证，后结论
10. 小错误若干：猜错同意版本号（查代码确认 `CONSENT_VERSION`）、构建时 dist 目录被瞬时文件锁（EPERM，重试即过）、首次下载 gh CLI 未注意命令行不走系统代理（显式设置代理后解决）

## 7. 我如何发现并纠正这些错误

| 发现方式 | 对应的错误 |
|---|---|
| 迁移前的**只读审计**（探索代理逐行核对部署依赖与评分键） | 5、6 |
| **测试先行**：每次改动后全量回归（48 单测 + 12 e2e + typecheck/lint/build） | 全部改动的通用防线 |
| **线上实测代替想当然**：对生产 URL 做真实请求、验证后自动撤回 | 7 |
| **读第三方源码定位根因**：读 wrangler 部署源码确认子域名调用是无条件的，而非配置问题 | 8 |
| **网络实证**：国内 DNS 查询 + 直连抓包 + 浏览器复测，推翻"被墙"的直觉 | 9 |
| 报错信息 + 代码核对 + 重试 | 10 |

纠正闭环：每个错误修复后都补回归测试（如"伪造身份头必须 401"进了单测和 e2e），确保同类问题不会悄悄回归。

## 8. 经验与未完成事项

**经验**：①把"验证 AI 输出"设计成独立步骤（审计报告、硬编码测试），而不是默认信任；②诊断问题先做最小实证（一次 curl、一次 nslookup）再下结论；③保持"失败即关闭"的默认安全姿态（未配置密码 = 后台锁定）。

**未完成**：10 名真实参与者的试用与反馈收集尚未开展——这是人工环节，AI 不能也不应替代。试用数据、后台汇总分析、技术报告的相应章节将基于真实数据补全。本文件不含任何虚构的参与者或反馈。
